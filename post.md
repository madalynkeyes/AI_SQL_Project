# Preach My Gospel App Database

My project models the data used and tracked by missionaries in the Preach My Gospel application. It covers the people being taught (friends) and the ward members who help them, along with lesson appointments, completed lessons, commitments, referrals, and baptism dates. The goal is for a missionary to ask plain-English questions like "Who is actively progressing?" or "Which lessons does Mia still need before baptism?" and get a plain-English answer.

**Code:** https://github.com/madalynkeyes/AI_SQL_Project
- [main.py](main.py): the chat loop (question → Gemini SQL → run on MySQL → Gemini friendly answer)
- [db.py](db.py): MySQL connection and schema/data loading
- [db_schema.sql](db_schema.sql) / [db_data.sql](db_data.sql): schema and fictional sample data
- [example_questions.md](example_questions.md): 6+ more example questions and results

**Model:** `gemini-3.1-flash-lite` through the `google-genai` Python SDK, with MySQL 8.0 as the database. This is the complete ERD split into three connected sections so the tables are easier to read. PK marks primary key; FK marks foreign key. Click any diagram to view it full size.

## How it works
1. When the app starts, it reads the live schema from `INFORMATION_SCHEMA` (tables, columns, types, primary and foreign keys) and sends it once, at the beginning of a Gemini chat session. It also tells Gemini to write only read-only MySQL `SELECT` queries and gives it one business rule: *"actively progressing" means a lesson completed or a commitment kept in the last 7 days.*
2. The user asks a question. Gemini returns SQL, and the user confirms before it runs.
3. The raw result rows go back into the same chat, and Gemini turns them into a friendly sentence.

## Query it did well on

**Question**: What members have interacted with Mia Chen and when?

**Gemini SQL Response**:
```sql
SELECT 
    m_p.first_name AS member_first_name, 
    m_p.last_name AS member_last_name, 
    i.occurred_at
FROM person p
JOIN friend_profile fp ON p.person_id = fp.person_id
JOIN interaction_friend ifr ON fp.person_id = ifr.friend_id
JOIN interaction i ON ifr.interaction_id = i.interaction_id
JOIN interaction_member im ON i.interaction_id = im.interaction_id
JOIN person m_p ON im.member_id = m_p.person_id
WHERE p.first_name = 'Mia' AND p.last_name = 'Chen';
```

**SQL Result**: [('Nora', 'Patel', datetime.datetime(2026, 10, 1, 18, 0)), ('Jonah', 'Reed', datetime.datetime(2026, 10, 2, 17, 30))]

**Friendly Response**: "Nora Patel interacted with Mia Chen on October 1, 2026, at 6:00 PM, and Jonah Reed interacted with Mia Chen on October 2, 2026, at 5:30 PM."

## Question that it tripped up on

**Question**: How many lessons have been scheduled for Mia Chen and how many were canceled or rescheduled?

**Gemini SQL Response**:
```sql
SELECT 
    COUNT(la.appointment_id) AS total_scheduled,
    SUM(CASE WHEN la.status IN ('canceled', 'rescheduled') THEN 1 ELSE 0 END) AS canceled_or_rescheduled
FROM person p
JOIN appointment_member am ON p.person_id = am.member_id
JOIN lesson_appointment la ON am.appointment_id = la.appointment_id
WHERE p.first_name = 'Mia' AND p.last_name = 'Chen';
```

**SQL Result**: [(0, None)]

**Friendly Response**: "The result [(0, None)] means that there are no lessons scheduled for Mia Chen, and therefore no lessons have been canceled or rescheduled for her."

**Expected**: It looks like AI misinterpreted the question. The correct answer is that we have had 1 lesson completed with Mia Chen, 1 lesson canceled and 1 lesson scheduled. It looks like the SQL query generated by AI joined the appointment_member table instead of the appointment_friend table. 

## Prompting strategies
The paper ([Chang & Fosler-Lussier, 2023](https://arxiv.org/abs/2305.11853)) compares **zero-shot**, **single-domain** (few-shot examples from the same database), and **cross-domain** (few-shot examples from a different database) prompting.

I tried all three. The strategy is set with `PROMPT_STRATEGY` at the top of [main.py](main.py), and the examples are added to the first message along with the schema.

- **Zero-shot**: My main approach. Gemini gets the schema, the instructions, and the business rule, but no example question/SQL pairs. This is what I used for the questions in [example_questions.md](example_questions.md).
- **Single-domain**: The same prompt plus two example question/SQL pairs written for my PMG database. They use a different friend (Leo Martinez) so they don't give away the answers to my test questions. One example finds a friend's appointments through `appointment_friend`, and the other finds which members attended lessons through `session_friend` and `session_member`.
- **Cross-domain**: The same prompt plus two example pairs from a made-up school database (students, teachers, and class meetings). Its join tables are set up like my friend and member tables, but none of the table names match.

I asked the question it tripped up on and the question it did well on with each strategy:

| Question | Zero-shot | Single-domain | Cross-domain |
|---|---|---|---|
| How many lessons have been scheduled for Mia Chen and how many were canceled or rescheduled? | Wrong: joined `appointment_member` and said Mia had no lessons | Mostly right: 3 lessons, 1 canceled or rescheduled | Mostly right: 3 lessons, 1 canceled or rescheduled |
| What members have interacted with Mia Chen and when? | Correct | Correct | Correct |

With either set of examples, Gemini joined `appointment_friend` instead of `appointment_member`, which fixed the mistake from the zero-shot run. Both answers were only "mostly" right because the query lumped canceled and rescheduled lessons into one count, so the answer couldn't say which one happened (it was a cancellation). The member question stayed correct under all three, so the examples didn't break anything that already worked.

Single-domain and cross-domain wrote nearly identical SQL. The one difference was in the friendly response: the cross-domain answer repeated the raw result (`[(3, Decimal('1'))]`) instead of only giving the plain-English sentence.

One thing that helped was adding the "actively progressing" business rule to the prompt. That phrase isn't a column anywhere, so without a definition the model has to guess what it means.

## Conclusion
Gemini did well with zero-shot prompting on most of my questions, even ones that needed several joins. The mistakes it made came from the schema design: friends and members each have their own junction table (`appointment_friend` and `appointment_member`, `session_friend` and `session_member`), and nothing in the schema says which one a question means. Adding two example queries was enough to point it at the right table. Examples from a completely different database worked just as well as examples from my own, so the model seems to be learning the pattern (follow the friend's join table) more than specific table names.

A remaining issue is that a wrong query can still produce a confident answer. In the zero-shot run, Gemini told me Mia had no lessons instead of noticing the result looked wrong. Because of that, I'd trust it for everyday questions, but for anything important someone who knows SQL should check the query (my app already shows it before running).
